# New store — measured before building

`P.newstore`, `/dashboard/stores/new`. Measured 2026-08-29.

---

## The form has four fields and the action reads three

`P.newstore` shows **Store name**, **Address**, **Phone** and **Lifecycle**
("Pre-open · skip forecasting").

`createStoreSchema` in `src/app/actions/store/crud-actions.ts` accepts
`name`, `address` and `phone`. There is no lifecycle in it, so
`Store.lifecycleStage` takes its schema default — `pre_open` — on every store
ever created.

That default is the right one, and the field is still wrong: a select that
looks like a choice and is not read is worse than a sentence saying the store
starts pre-open. The page states it instead.

## What each field actually switches on

The prototype's three notes are checkable, and two of the three hold:

**A — "Address turns on weather and events."** True. All three stores are
geocoded, via nominatim:

| store | lat, long | provider score |
|---|---|---:|
| Hollywood | 34.0982, −118.3105 | 0.00001 |
| Glendale | 34.1417, −118.2714 | 0.0534 |
| Van Nuys | 34.2013, −118.4519 | 0.00001 |

The score is nominatim's *importance* — a prominence measure for the matched
place, not an accuracy figure — so a low number on a street address is normal
and not a fault. `StoreWeatherSignal` holds 21,216 rows, so the feed works.
The events half does not, for an unrelated reason: PredictHQ last wrote a row
on 10 August and every run since has failed (see the model health page).

**B — "Lifecycle decides what the model does."** True, and stored:
`Store.lifecycleStage` is a real column read by `src/lib/store-lifecycle.ts`,
which is what stops a pre-open store rendering as healthy. It just cannot be
set at create time.

**C — "Rent and commissions decide whether the P&L is true."** True, and this
is where the live account stands:

| input | Hollywood | Glendale | Van Nuys |
|---|---|---|---|
| Monthly rent | $10,390 | **not set** | **not set** |
| Fixed monthly labour | **$0** | not set | not set |
| Cleaning | $3,400 | not set | not set |
| Linen | $238.33 | not set | not set |
| COGS target | 30% | **not set** | **not set** |
| Uber / DoorDash | 21% / 25% (defaults) | defaults | defaults |
| Otter link | linked, syncing | linked, syncing | linked, syncing |
| Harri link | linked | **none** | **none** |
| Phone | none | none | none |

Hollywood's labour is **0, not null** — set to zero rather than left unset,
which reads as "no salaried cost" and may well be a field someone tabbed past.
The two pre-open stores carry no fixed costs at all, which is correct while
they are not trading and becomes wrong the day they open.

## The checklist can be real

The prototype's "not required now, but before opening" table is six invented
rows with invented states. Every one of them is measurable on the stores that
exist, so the page shows the account's actual readiness rather than a mock —
and that is more useful on a create form than a fictional checklist, because
the two stores it describes are opening.

`StoreFixedExpense`, incidentally, holds **0 rows**. The fixed-cost model in
use is the four `fixedMonthly*` columns on `Store`.

## One dead gate

The editorial page calls `hasOwnerAccess(session.user.role)` and redirects on
failure. `Role` holds only `OWNER` and `DEVELOPER` and the helper accepts
both, so the branch is unreachable. Not carried over. `createStore` itself
still checks it server-side, which is where a real gate belongs.
