# Settings — measured before building

`P.settings`, `/dashboard/settings`. Measured 2026-08-29.

The prototype makes this **one page** with six panels. The editorial build
spread it over four routes — `/settings`, `/settings/account`,
`/settings/notifications`, `/settings/preferences`. The rebuild follows the
prototype: one page.

---

## The owner's clock is on the wrong coast

| account | role | timezone | owns stores |
|---|---|---|---|
| `chris@chrisneddys.com` | OWNER | **America/New_York** | none |
| `demo@restaurantos.com` | DEVELOPER | America/Los_Angeles | all three |

Every store is in Los Angeles. The owner's `User.timezone` is New York — the
schema default (`@default("America/New_York")`) never changed. Anything that
buckets a date by the signed-in user's timezone puts the owner three hours
ahead of his own restaurant, which is the same class of fault as the four
monitoring components that bucket in server-local time under a "PT" masthead.

And all three stores are owned by the developer account. `Store.ownerId`
points at `demo@`, not at the owner.

## Four notification toggles, three of which exist

The prototype offers **Daily digest**, **Critical alerts**, **Invoice
review** and **Weekly decisions**.

`AlertPreference` — the table built for exactly this — holds **0 rows**. What
does exist is three booleans on `User`, all currently true:

| field | prototype's name |
|---|---|
| `notifyInvoices` | Invoice review |
| `notifyWeeklyReport` | Weekly decisions |
| `notifyAnomaly` | Critical alerts |

There is no daily digest. `updateNotificationPrefs` in
`src/app/actions/user-actions.ts` writes the three that exist, so three
toggles work and the fourth is not drawn.

## The sessions panel has no sessions

The prototype lists devices with an **End** button and a **Sign out
everywhere**. Auth is JWT — the schema says so in `LoginEvent`'s docblock:
*"we use JWT strategy, so there is no Session table to enumerate"*. Presence
is derived from a `SIGN_IN` with no later `SIGN_OUT`.

In the last thirty days: **727 SIGN_IN events and 0 SIGN_OUT.** Not a low
number — zero. So every sign-in ever recorded still reads as live, and a
"your devices" list built on this would show 727 open sessions across six
user agents, 687 of them one Linux automation client.

There is nothing to end and nothing to sign out of. The panel is replaced by
what the data can answer: where sign-ins came from, and how many.

## Nothing issues an invite

The prototype's own source carries the note: *"There is an invite record, a
signup page and a route that redeems a token — and nowhere that issues one."*

Confirmed. `Invite` holds **4 rows**, and `prisma.invite.create` appears
nowhere in `src/` outside the generated client. The **Invite someone**,
**Resend** and **Revoke** buttons have no action behind any of them.

## And there is no manager to invite

The prototype's Team panel shows a Manager with one store, and says *"a
manager sees one store and cannot open Settings or Monitoring."*

The `Role` enum in the live database has exactly two values: `OWNER` and
`DEVELOPER`. There is no MANAGER. Every `hasOwnerAccess` gate in the codebase
accepts both of them, so no gate in this product can fail.

## What the page can honestly show

- Account: name, email, role, the timezone (flagged), which stores the account
  can see (3 of 3).
- Notifications: the three toggles that write.
- Sign-ins: user agents and counts, with the zero-sign-out caveat stated.
- Preferences: `User.timezone` is the only stored preference. Week start,
  currency, density and theme are not stored anywhere — Counter ships a light
  and a dark theme, asserted by test, and the theme follows the viewer.
- Team: the two real accounts and the four invite rows, with the note that
  nothing issues one.
